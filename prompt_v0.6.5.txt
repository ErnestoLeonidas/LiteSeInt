Implementa la versión 0.6.5 de LiteSeInt: "Base educativa".

Contexto del proyecto:
- LiteSeInt es una plataforma minimalista para programar en pseudolenguaje, aprender los comandos y ejercitar con una ruta progresiva.
- La versión 1.0 debe servir para que un estudiante parta desde cero, practique con ejercicios graduados y construya una base para aprender Python.
- El archivo `ejercicios/guia.html` es la fuente pedagógica principal para el roadmap de aprendizaje, pero su estructura visual es solo referencial.
- Lo importante de `guia.html` son sus ejercicios, su secuencia, sus niveles de complejidad y los comandos que enseña.
- Todos los ejercicios que se integren desde `guia.html` deben adaptarse al lenguaje definido por LiteSeInt.

Antes de editar:
1. Lee `CLAUDE.md`.
2. Lee `.claude/skills/liteseint-language-change/SKILL.md`.
3. Lee `ROADMAP.md`.
4. Lee `README.md`, `CHANGELOG.md`, `index.html`, `js/doc_errores.js`, `js/LiteSeInt.js`, `js/app.js`, `tests/run-tests.js` y `ejercicios/guia.html`.
5. Revisa cambios locales no relacionados con `git status`. No reviertas cambios de otros.

Objetivo de 0.6.5:

Preparar LiteSeInt para la integración educativa posterior. Esta fase debe dejar documentado, medible y verificable cómo se adaptarán los ejercicios de `ejercicios/guia.html` al dialecto LiteSeInt.

Alcance exacto:

1. Confirmar el lenguaje LiteSeInt actual.
   - Revisar qué comandos soporta realmente el runtime.
   - Revisar qué comandos valida `js/doc_errores.js`.
   - Revisar qué palabras aparecen en autocompletado.
   - Revisar qué documenta `README.md`.
   - Identificar contradicciones, si existen.

2. Analizar `ejercicios/guia.html`.
   - Extraer o resumir su estructura pedagógica:
     - experiencias de aprendizaje;
     - cantidad aproximada de ejercicios por experiencia;
     - niveles de dificultad;
     - comandos y conceptos usados.
   - No copies su estructura visual.
   - No conviertas todavía toda la guía en UI nueva.
   - Usa la guía como fuente de contenido y secuencia, no como diseño final.

3. Definir reglas obligatorias de adaptación de ejercicios.
   Documentar reglas para convertir todos los ejercicios visibles al dialecto LiteSeInt:
   - `Cadena` -> `Caracter`
   - `<-` -> `=`
   - `SiNo` -> `Sino`
   - `MOD` -> `mod`
   - `DIV` -> reescribir usando sintaxis soportada o excluir temporalmente ejercicios que lo requieran
   - cualquier sintaxis fuera de LiteSeInt debe adaptarse, no dejarse tal cual.
   - no agregar alias ni sintaxis nueva solo porque aparezca en `guia.html`.

4. Agregar estas reglas al proyecto.
   - Actualizar `README.md` o crear un documento dedicado si queda mejor.
   - Actualizar `ROADMAP.md` si falta precisión.
   - Actualizar `CHANGELOG.md` con entrada `0.6.5`.
   - Actualizar versión visible a `v0.6.5` solo si la fase queda completa.

5. Agregar un plan de pruebas para ejercicios.
   Debe quedar claro que la adaptación de ejercicios es parte del plan de pruebas, no una tarea informal.
   Incluir como mínimo:
   - prueba de conversión de sintaxis;
   - prueba de validación estática para código de referencia adaptado;
   - prueba de ejecución para ejercicios principales;
   - prueba de salida esperada cuando existan entradas de ejemplo;
   - prueba de cobertura pedagógica por comando;
   - criterio de exclusión documentada para ejercicios que aún no puedan adaptarse.

6. Crear o preparar una estructura inicial de seguimiento si conviene.
   Opciones aceptables:
   - una tabla en documentación;
   - un checklist;
   - un archivo `.md` dedicado;
   - una sección en `README.md`.
   Debe permitir responder:
   - qué ejercicios ya están adaptados;
   - qué ejercicios requieren decisión de lenguaje;
   - qué ejercicios quedan excluidos temporalmente;
   - qué comandos cubre cada módulo.

No hacer en 0.6.5:
- No mover la consola debajo del editor. Eso pertenece a 0.7.0.
- No rediseñar el layout principal.
- No implementar el panel derecho de ejercicios.
- No convertir los 245 ejercicios completos en esta fase salvo que el cambio sea puramente documental o de extracción segura.
- No implementar arreglos, matrices, `SubProceso` ni funciones definidas por usuario.
- No portar código C++ de PSeInt.
- No agregar backend ni build step.
- No cambiar el objetivo minimalista del proyecto.

Decisiones importantes:
- Para 1.0, los ejercicios se adaptan a LiteSeInt. LiteSeInt no debe crecer sin control para aceptar todo lo que aparezca en la guía.
- La sintaxis definida en `guia.html` no debe usarse como fuente de verdad del lenguaje.
- No implementar alias para `Cadena`, `<-`, `SiNo`, `MOD` o `DIV` en 0.6.5. Esas formas deben convertirse al lenguaje LiteSeInt o dejar el ejercicio como pendiente/excluido.
- Si un ejercicio requiere algo fuera de alcance, debe quedar marcado como "requiere adaptación" o "excluido temporalmente", no visible como ejercicio listo.

Criterios de aceptación:
- `ROADMAP.md` mantiene el foco educativo hacia 1.0.
- Existe una definición clara de cómo adaptar ejercicios de `guia.html` al dialecto LiteSeInt.
- Existe un plan de pruebas para ejercicios adaptados.
- La documentación menciona que el 100% de ejercicios visibles deben estar adaptados o explícitamente excluidos.
- `CHANGELOG.md` incluye la entrada de `0.6.5`.
- La versión visible queda en `v0.6.5` si todo lo anterior se completa.
- `npm test` pasa, o se informa claramente si no se pudo ejecutar.

Verificación sugerida:
- Ejecutar `npm test`.
- Revisar manualmente que la app siga abriendo.
- Revisar que README/ROADMAP/CHANGELOG no se contradigan.
- Revisar que las reglas de adaptación indiquen explícitamente cómo reemplazar o excluir sintaxis de `guia.html` que no pertenece a LiteSeInt:

  - `<-` debe convertirse a `=`;
