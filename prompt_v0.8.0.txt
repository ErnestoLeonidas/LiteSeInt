Implementa la versión 0.8.0 de LiteSeInt: "Banco de Ejercicios Integrado".

Contexto del proyecto:
- LiteSeInt es una plataforma minimalista para programar en pseudolenguaje, aprender comandos y ejercitar.
- La versión 0.7.0 reorganizó la interfaz: editor como columna principal, consola debajo del editor y redimensionable, panel derecho reservado para aprendizaje/ejercicios y ejemplos en un menú desplegable arriba del editor.
- La versión 0.8.0 debe reemplazar los placeholders del panel derecho por un banco real de ejercicios navegable, derivado de `ejercicios/guia.html` y adaptado al dialecto LiteSeInt.
- El lenguaje LiteSeInt ya está definido. No agregues sintaxis nueva ni alias para calzar con `ejercicios/guia.html`.

Antes de editar:
1. Lee `CLAUDE.md`.
2. Lee `.claude/skills/liteseint-language-change/SKILL.md` si existe.
3. Lee `ROADMAP.md`.
4. Lee `EJERCICIOS.md`.
5. Lee `README.md`, `CHANGELOG.md`, `index.html`, `css/styles.css`, `js/app.js`, `js/doc_errores.js`, `js/LiteSeInt.js` y `tests/run-tests.js`.
6. Revisa `prompt_v0.7.0.txt` para mantener continuidad de estilo y decisiones.
7. Revisa `ejercicios/guia.html` como fuente pedagógica.
8. Revisa cambios locales con `git status`. No reviertas cambios no relacionados.

Objetivo de 0.8.0:

Convertir `ejercicios/guia.html` en un banco de ejercicios integrado a LiteSeInt:

- fuente de datos mantenible dentro del proyecto;
- ejercicios normalizados por campos;
- todos los ejercicios visibles adaptados al dialecto LiteSeInt;
- navegación por nivel/módulo, dificultad, conceptos y estado;
- detalle del ejercicio en el panel derecho;
- progreso local persistente en el navegador.

Alcance exacto:

1. Extraer ejercicios desde `ejercicios/guia.html`.
   - Analizar la estructura real del HTML antes de decidir la estrategia.
   - Crear una fuente de datos mantenible dentro del proyecto, por ejemplo:
     - `js/ejercicios-data.js`, si se integra como módulo/carga directa en la app;
     - o `ejercicios/ejercicios.json`, si se decide cargar datos estructurados;
     - o ambos, si conviene separar generación y consumo.
   - La app debe consumir datos normalizados, no parsear `guia.html` en runtime.
   - Si crear un script de extracción ayuda, ubicarlo de forma clara, por ejemplo `tools/extraer-ejercicios.js`. No agregar build step obligatorio para usar la app.

2. Normalizar campos de cada ejercicio.
   Cada ejercicio integrado debe tener al menos los campos definidos en `EJERCICIOS.md`:
   - `id`;
   - `origen`;
   - `modulo`;
   - `nivelLiteSeInt`;
   - `experiencia`;
   - `dificultad`;
   - `gradoAyuda`;
   - `titulo`;
   - `conceptos`;
   - `enunciado`;
   - `entradaProcesoSalida`;
   - `salidaEsperada`;
   - `pista`;
   - `codigoReferencia`;
   - `estadoAdaptacion`;
   - `motivoExclusion`.

   Reglas:
   - `id` debe ser estable y legible, por ejemplo `ea1-1-001`.
   - `conceptos` debe usar nombres consistentes: `Escribir`, `Leer`, `Definir`, `Si`, `Mientras`, `Para`, `Segun`, `contador`, `acumulador`, etc.
   - `nivelLiteSeInt` debe mapear el ejercicio a los niveles 0-9 definidos en `EJERCICIOS.md` y `ROADMAP.md`.
   - `gradoAyuda` debe usar la progresión: `guiado`, `con-pista`, `practica`, `desafio`.
   - `dificultad` debe ser `basico`, `intermedio` o `avanzado`.
   - `estadoAdaptacion` debe ser uno de: `adaptado`, `requiere-decision`, `excluido-temporal`.

3. Adaptar ejercicios al dialecto LiteSeInt.
   Aplicar obligatoriamente las reglas de `EJERCICIOS.md`:
   - `Cadena` -> `Caracter`;
   - `<-` -> `=`;
   - `SiNo` -> `Sino`;
   - `MOD` -> `mod`;
   - quitar `;` final;
   - `=` como comparador en condiciones -> `==`;
   - `DIV` -> `Trunc(a / b)` cuando sea pedagógicamente correcto, o marcar como `excluido-temporal`;
   - `Escribir Sin Saltar` -> reescribir la salida si es razonable, o excluir temporalmente;
   - `Leer x, y` -> `Leer x` y `Leer y` en líneas separadas.

   No hacer:
   - No agregar alias al runtime para `Cadena`, `<-`, `SiNo`, `MOD` o `DIV`.
   - No ampliar el lenguaje para hacer pasar la guía.
   - No mostrar ejercicios con sintaxis no soportada.
   - No dejar visible un ejercicio en estado intermedio.

4. Definir política realista para el volumen inicial.
   - El roadmap menciona los 245 ejercicios, pero la regla de calidad manda: todo ejercicio visible debe estar adaptado.
   - Si el tiempo no alcanza para adaptar y probar los 245, integra un primer lote sólido y registra el resto como pendiente/no visible.
   - El primer lote debe cubrir al menos los niveles iniciales 0-4 y algunos ejercicios de ciclos si es viable.
   - Si decides integrar los 245, todos los visibles deben pasar por adaptación y revisión automática o manual documentada.
   - En la interfaz, muestra solo `adaptado`. Los `requiere-decision` y `excluido-temporal` pueden aparecer en una vista interna/resumen, pero no como ejercicios listos para estudiantes.

5. Reemplazar placeholders del panel derecho.
   - El panel derecho de 0.7.0 debe mostrar ejercicios reales.
   - Debe permitir navegar o filtrar por:
     - módulo/nivel LiteSeInt;
     - dificultad;
     - conceptos;
     - estado de progreso: pendiente, en curso, completado.
   - Debe conservar la ruta de aprendizaje 0-9 como estructura principal o como filtro claro.
   - Al seleccionar un ejercicio, mostrar:
     - título;
     - dificultad;
     - nivel/módulo;
     - conceptos;
     - enunciado;
     - entrada/proceso/salida cuando exista;
     - salida esperada;
     - pista opcional;
     - botón para cargar plantilla o código de referencia si corresponde.
   - La solución/código de referencia no debe estar visible por defecto. Debe ser ayuda opcional.

6. Integrar acciones del ejercicio con el editor.
   - Agregar acción para cargar una plantilla o código inicial en el editor.
   - Si un ejercicio tiene `codigoReferencia`, permitir cargarlo sólo como ayuda explícita, no automáticamente al seleccionar.
   - Evitar sobrescribir código del estudiante sin confirmación o sin una acción clara.
   - Mantener intactos los ejemplos del selector superior.

7. Progreso local.
   - Permitir marcar ejercicios como:
     - pendiente;
     - en curso;
     - completado.
   - Guardar progreso en `localStorage`, con una clave estable, por ejemplo `liteseint:exerciseProgress`.
   - El progreso debe conservarse al recargar la página.
   - Mostrar conteo simple de avance por módulo/nivel.
   - Permitir filtrar por estado.
   - No es necesario validar automáticamente si la solución del estudiante es correcta en 0.8.0.

8. Responsive y UX.
   - En escritorio, el panel derecho debe seguir siendo usable sin comprimir demasiado el editor.
   - En móvil, los filtros y el detalle del ejercicio deben poder leerse sin tapar editor/consola.
   - Evitar cards anidadas o una UI pesada. La app debe seguir minimalista.
   - Mantener acciones principales visibles: ejecutar, detener, borrar, descargar, seleccionar ejemplo, limpiar consola.

9. Pruebas.
   - Agregar pruebas para validar la estructura del banco de ejercicios:
     - ids únicos;
     - campos obligatorios presentes;
     - sólo estados permitidos;
     - sólo dificultades permitidas;
     - sólo grados de ayuda permitidos;
     - todo ejercicio visible está `adaptado`;
     - ningún `codigoReferencia` adaptado contiene `<-`, `Cadena`, `SiNo`, `MOD`, `DIV` ni `;` final;
     - condiciones con igualdad usan `==` cuando corresponda.
   - Si es viable, ejecutar `DocErrores.validarDocumento(codigoReferencia)` para los códigos adaptados que estén completos.
   - Mantener y ejecutar `npm test`.

10. Documentación y versión.
    - Actualizar `README.md` para describir el banco de ejercicios integrado, filtros y progreso local.
    - Actualizar `EJERCICIOS.md` con el estado real de integración:
      - cantidad de ejercicios adaptados;
      - cantidad pendiente;
      - cantidad excluida temporalmente;
      - criterios usados para el primer lote si no se integran los 245.
    - Actualizar `CHANGELOG.md` con entrada `0.8.0`.
    - Actualizar versión visible en `index.html` a `v0.8.0` sólo si el banco navegable, progreso local y pruebas quedan completos.

No hacer en 0.8.0:
- No implementar documentación completa de comandos en la app; eso pertenece a 0.8.5.
- No implementar "Roadmap del estudiante" completo más allá de lo necesario para navegar ejercicios.
- No implementar puente a Python; eso pertenece a 0.9.5.
- No agregar backend, login, base de datos ni dependencias pesadas.
- No reescribir el runtime.
- No cambiar el dialecto LiteSeInt para aceptar sintaxis PSeInt clásica.
- No mostrar soluciones automáticamente al estudiante.
- No implementar corrección automática avanzada de ejercicios.

Criterios de aceptación:
- Existe una fuente de datos mantenible para ejercicios.
- El panel derecho muestra ejercicios reales, no sólo placeholders.
- El estudiante puede filtrar/navegar por módulo o dificultad.
- Al seleccionar un ejercicio, ve enunciado y salida esperada.
- El estudiante puede marcar progreso y ese progreso se conserva al recargar.
- El listado distingue pendiente/en curso/completado.
- Todo ejercicio visible está adaptado al dialecto LiteSeInt.
- Las soluciones o códigos de referencia visibles como ayuda no usan sintaxis fuera de alcance.
- README, EJERCICIOS, CHANGELOG e interfaz reflejan `v0.8.0`.
- `npm test` pasa o se informa claramente si no pudo ejecutarse.

Verificación sugerida:
1. Ejecutar `npm test`.
2. Abrir `index.html` y probar manualmente:
   - seleccionar un módulo/nivel;
   - filtrar por dificultad;
   - seleccionar un ejercicio;
   - leer enunciado y salida esperada;
   - cargar plantilla o ayuda si existe;
   - escribir una solución simple;
   - ejecutar;
   - marcar en curso/completado;
   - recargar la página y confirmar que el progreso persiste;
   - filtrar por completados y pendientes.
3. Revisar al menos un ejercicio con `Leer` y confirmar que la consola inferior conserva el input inline.
4. Revisar responsive en ancho móvil desde DevTools si es posible.
5. Confirmar que no cambió la sintaxis del lenguaje.

- Limitaciones que quedan para 0.8.5, 0.9.0 y siguientes.
